# 06. AI への指示とベストプラクティス

## ゴール

ここまでの全章を、**AI への指示の出し方**という観点で総まとめする。AI 駆動開発の生産性は、コードを書く力ではなく**指示とレビューの質**で決まります。

---

## 大原則：AI に「方針」を渡し、「判断」は人間が持つ

AI はコードを書けますが、**何を選ぶか・どう構成するかは人間が決める**領域です（第 01〜02 章）。指示には次を含めると精度が上がります。

1. **方式の明示** … 「Composition API（`<script setup>`）で」
2. **使う技術の明示** … 「Orval で生成、MSW でモック」
3. **挙動の具体化** … 「401 ならリフレッシュして 1 回だけリトライ」
4. **制約** … 「生成物（`src/api/generated/`）は編集しない」

---

## 良い指示 vs 曖昧な指示

| 場面 | 曖昧な指示（避ける） | 良い指示 |
|------|---------------------|----------|
| コンポーネント | 「Vue で一覧画面作って」 | 「Composition API の `<script setup>` で、棋譜一覧を表示するコンポーネントを作って。データは `src/api/generated` のクライアント経由で取得」 |
| 状態共有 | 「グローバルな状態作って」 | 「Pinia は使わず、`ref` を module スコープに置く Composable で共有して。外には `readonly` で公開」 |
| API 変更 | 「レスポンスに項目足して」 | 「`docs/openapi_main.yaml` に項目を足して、`npm run generate:api` で再生成して。生成物は直接編集しない」 |
| 認証 | 「ログイン機能つけて」 | 「Cognito の Authorization Code + PKCE フローで。トークンは sessionStorage、認可はルートガード（`meta.requiresAuth` + `beforeEach`）で」 |

> 共通点：**良い指示は「技術名・方式・挙動・制約」が具体的**。これは第 01〜05 章で学んだ判断を、そのまま言語化したものです。だから本教材は文法でなく**判断**を扱ってきました。

---

## ベストプラクティス集（横断）

### 1. 生成物は触らない・直すなら元を直す

`Do not edit manually` のファイルは編集しない。API を変えたいなら **OpenAPI（YAML）を直して再生成**（第 04 章）。AI にも「生成物は編集禁止、YAML を直して」と伝える。

### 2. 型で守る

TypeScript を全面採用し、AI が書いたコードも型エラーで検出する。**`npm run build`（型チェック込み）が通って初めて「動く」**とみなす（第 03 章）。

### 3. モックは固定とランダムを使い分ける

UI 確認に使うデータは手書きで固定、それ以外は生成のランダムでよい（第 04 章）。AI には「この画面の確認用に固定データを `browser.ts` に足して」と頼む。

### 4. 認証は IdP 委譲・フロー名を明示・必ずレビュー

自前実装させない。フロー名（PKCE 等）と挙動を具体的に指示し、**生成結果は人間がレビュー**（第 05 章）。セキュリティに直結する箇所は丸投げしない。

### 5. コマンドの確認は人間がやる

AI が「実装しました」と言っても、`npm run lint` / `test` / `build` は**人間が叩いて確認**する（第 03 章）。AI の自己申告を鵜呑みにしない。

### 6. ルールはファイルに書いて毎回言わない

「Composition API を使う」「生成物は触らない」のような恒久ルールは、毎回指示するのではなく **`CLAUDE.md` / `AGENTS.md` などのルールファイル**に書いておくと、AI が常に従います（ShogiProject も `AGENTS.md` で規約を集約）。

## 演習：1 つの機能を「指示 → 確認」で完成させる

第 00 章の `learning-vue` で、AI に小さな機能を作らせ、人間が確認するループを 1 周回します。

1. **指示を書く**（例）:
   ```
   Composition API の <script setup> で、ボタンを押すとカウントが増える
   コンポーネントを作って。状態は useCounter Composable（ref を module
   スコープに置く）で共有して、2 つ配置しても同じ値になるようにして。
   ```
2. AI に実装させる
3. **人間が確認**:
   ```bash
   npm run dev     # 画面で 2 つのカウンタが連動するか
   npm run lint    # Lint が通るか
   npm run build   # 型チェック込みで通るか
   ```
4. 落ちたらエラーを AI に渡して直させる

このループ（**指示 → 生成 → コマンドで確認 → フィードバック**）が AI 駆動開発の基本リズムです。

## 全体のまとめ

この教材で扱ったのは、AI 駆動開発で**人間が担う層**でした。

| 章 | 人間が持つべき判断 |
|----|--------------------|
| 00 | 雛形生成と初期構成の選択 |
| 01 | Composition API・状態管理・分割の設計判断 |
| 02 | 各カテゴリのツール選定 |
| 03 | どのコマンドをいつ叩くか |
| 04 | スキーマ駆動の運用、生成と手書きの境界 |
| 05 | 認証・認可のパターンとレビュー |
| 06 | 指示の具体化とベストプラクティス |

**文法は AI に任せ、判断と指示とレビューを人間が持つ。** これが AI 駆動開発における Vue 開発の要点です。

実プロジェクトの実例は、いつでも `shogi-main/` の該当ファイルを開いて確認してください。本教材の各章末に「ShogiProject ではどうしているか」を置いてあります。
